In this case study, we migrate **[Padmark](https://github.com/lambdapad/padmark)** — a pure-Elixir Markdown parser and HTML transformer with `leex`/`yecc` lexers and parsers (**81 BEAM modules**) — from **Dialyzer** (`dialyxir`) to **[Prisma](https://prisma.altenwald.com/)**.

Running both tools side by side on Elixir `1.20.4` / OTP `29.1.2` highlights two complementary differences: **Dialyzer** took **1m 18.57s** on a cold PLT build (`2.13s` warm) and reported **0 errors**, whereas **Prisma** completed its cold dependency PPLT build + analysis in **9.76s** (`0.95s` warm) and uncovered **5 real issues** — two `@spec` bugs (one causing `dead_code`) and three unused private-function parameters (`oxbow_code`) — plus an upstream Elixir stdlib spec imprecision in `Regex.run/2` and `Regex.scan/2` that we submitted in **[elixir-lang/elixir#16151](https://github.com/elixir-lang/elixir/pull/16151)**.

## 2. What Prisma Caught That Dialyzer Missed

Dialyzer's success typing leaves wide or mismatched `@spec`s silent as long as *some* execution path can succeed. Prisma's hybrid mode caught **5 genuine issues** in Padmark:

### A. `@spec` Mismatches & Dead Code (2)

1. **`Padmark.Helpers.replace/4` (`lib/padmark/helpers.ex:7`)**
   - **Declared:** `@spec replace(String.t(), Regex.t(), String.t() | (... -> String.t()), Padmark.Options.options()) :: String.t()`
   - **Actual:** `Padmark.Helpers.replace/4` forwards `options` straight to `Regex.replace/4`, whose spec expects `global: boolean()` — not `%Padmark.Options{}` structs or maps.
   - **Fix:** Narrowed the 4th parameter spec to `global: boolean()`.

2. **`Padmark.Transform.transform/2` (`lib/padmark/transform.ex:266`) — `dead_code`**
   - **Declared:** `@spec transform(Padmark.ast(), Options.options()) :: String.t()`
   - **Actual:** The docstring states it *"also accepts the result of `map_ast_with` for convenience"*, and the very first clause is `def transform({ast, _}, options)`. Because `Padmark.ast()` is a list, Prisma flagged that clause as unreachable (`Function clause pattern cannot match`).
   - **Fix:** Widened the first parameter spec to `Padmark.ast() | {Padmark.ast(), term()}`.

### B. Unused Private Parameters (`oxbow_code`, 3)

3. **`Padmark.Parser.Ast.Inline.footnote_link/3` (`lib/padmark_parser/ast/inline.ex:397`)**: `_match` (argument #2) was ignored across all clauses -> simplified to `footnote_link/2`.
4. **`Padmark.Parser.Parser.ListParser._finish_list_item/3` (`lib/padmark_parser/parser/list_parser.ex:195`)**: `_at_start?` (argument #2) was ignored and forwarded through `_finish_list_items/4` -> removed from both helpers.
5. **`Padmark.Transform._make_att1/2` (`lib/padmark/transform.ex:484`)**: `tag` (`_`) (argument #2) was ignored -> simplified to `_make_att1/1`.

## 3. From a False Positive in Padmark to an Upstream Elixir PR

The remaining 5 findings in `Padmark.Parser.LineScanner` (`lib/padmark_parser/line_scanner.ex`) all came from calling `Regex.run/2` (via `regex_run(key, target)` -> `Regex.run(rgx_map(key), target, [])`) and then passing the captured groups to `String.length/1`, `String.trim/1`, and `String.starts_with?/2`:

```elixir
@spec run(t, binary, capture_opts) :: nil | [binary] | [{integer, integer}]
def run(regex, string, options \\ [])
```

Because Elixir defines `Regex.run/2` via a default argument `options \\ []`, the 2-arity function inherited `[{integer, integer}]` in its return union — even though `Regex.run/2` without `return: :index` can **never** return index tuples. Dialyzer stays silent because `[binary]` overlaps `String.t()`, whereas Prisma's `gradual_mismatch` rejects `{integer(), integer()} | String.t()` where `String.t()` is expected.

Running Prisma across Elixir's own `lib/elixir/ebin` (`2.68s` for the entire standard library) confirmed the same pattern in `Regex.run/2` and `Regex.scan/2`, along with several unused private parameters (`Calendar.ISO.zone_to_iodata/4`, `GenEvent.server_update/5`, `GenEvent.server_call_update/4`, `Registry.Partition.init_pid_ets/2`, `Code.Formatter.unary_op_to_algebra/5`, and `Code.Fragment.codepoint_cursor_context/2`). Those fixes were submitted upstream in **[elixir-lang/elixir#16151](https://github.com/elixir-lang/elixir/pull/16151)**.

## 4. Engineering Bonus Along the Way

Benchmarking `padmark`'s dependencies and Elixir's standard library during this migration also surfaced two major performance bugs in Prisma itself:

- **Exponential `andalso`/`orelse` re-evaluation (`v0.2.5`)**: Building Elixir's 271-module `.pplt` dropped from **2m 11.98s** to **1.95s** (~68× faster; `Elixir.Calendar.ISO` alone dropped from **124s** to **15.1ms**).
- **Infinite recursion in `tuple_combinations/1` (`v0.2.6`)**: Building the `.pplt` for `erlex 0.2.9` (`erlex_parser.beam`) dropped from a >6-minute hang to **0.25s**.
- **Community issue sweep (`v0.2.7`)**: All 16 open issues (`#1`–`#16`) were verified, resolved, and covered with regression tests (**290 EUnit tests**, **18/18 PropEr properties** passing).
